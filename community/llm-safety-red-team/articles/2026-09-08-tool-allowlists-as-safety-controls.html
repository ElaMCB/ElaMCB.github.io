Treat Tool Allowlists Like Production Feature Flags

A refused answer with a still-executed tool call is not a pass. Make allowlists first-class safety controls with owners and tests.

Refusal text is not containment

If the model says no but still calls CRM, calendar, or shell tools, you failed the safety case. Screenshots of the chat hide the tool span. Your gate must fail when a disallowed tool runs—not when the prose looks polite.

Write the allowlist as an artifact: which tools exist, who may invoke them, under which intents, and what arguments are forbidden. Version it next to the agent config the same way you version feature flags.

Minimum viable allowlist checks

Block tools not on the list. Block argument shapes that exfiltrate (raw account IDs plus PII fields, unrestricted SQL, file paths outside the sandbox). Log every deny with the prompt id and span id so Security can audit.

Add three CI probes: (1) injection that asks for a blocked tool, (2) legitimate intent that needs an allowed tool, (3) refusal-with-tool-leak regression from your last incident. Automate the first and third; keep the second as a smoke test.

Ownership

Name a QA owner for the probe set and a platform owner for the allowlist code. When a new tool ships, both must sign off before production—same bar as opening a new network egress.
